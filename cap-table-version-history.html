Why the record drifts

A spreadsheet only shows the last save.

Every new tab, every overwritten cell, and every emailed copy erases the version that came before it. When someone asks what changed since the last round, the answer usually depends on whoever still has the old file.

A recorded transaction history keeps every change in place instead of overwriting it.

Three different things

Transactions, versions, and exports are not the same record.

Keeping them distinct is what makes the history useful instead of confusing.

①

Transactions

A single recorded event: an issuance, a transfer, a grant, or a conversion. Each one is logged on its own.

②

Version snapshots

The state of the whole cap table at a point in time, built from the transactions recorded up to that point.

③

Exports

A copy of a version pulled out for sharing, such as a document handed to an investor or an advisor.

Review, not reconstruction

See what changed, who it affected, and when.

Each version lists the transactions that produced it, a plain-language summary of the change, and the ownership context it affected. Founders review their own history; advisors review the same history across every client they support.

  • ✓ Every version linked back to the transactions that built it
  • ✓ Change summaries in plain language, not raw ledger entries
  • ✓ Ownership context shown alongside each change

For CFOs, advisors & accountants

The same history, across every client.

When a client asks what changed since the last time you looked, the version history has the answer without a call to the founder. Review is separate from writing to the ledger, so nothing changes until the client commits it.
